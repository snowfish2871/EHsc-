# EHsc文件哈希校验

一个基于 **Windows + C++17** 的离线文件哈希计算与比较工具。

本项目不依赖 OpenSSL、CryptoAPI、Boost 或其他第三方库，内置实现以下校验算法：

- CRC32
- MD5
- SHA-1
- SHA-256
- SHA-384
- SHA-512

程序提供 Windows 原生文件选择窗口，支持 Unicode 文件路径，可用于文件完整性校验、文件传输验证、备份文件核对以及两个文件的内容比较。

## 项目特点

### 1. 完全离线运行

程序只访问用户主动选择的本地文件，不访问互联网，也不会将文件内容、路径或哈希值上传到远程服务器。

适用于以下场景：

- 内网环境；
- 无网络环境；
- 对文件隐私有要求的环境；
- 需要本地处理敏感文件的场景；
- 软件包或备份文件的完整性检查。

### 2. 不依赖第三方库

哈希算法均在项目源码中实现，不依赖：

- OpenSSL；
- Windows CryptoAPI；
- Boost；
- Crypto++；
- 第三方 GUI 框架；
- 其他外部运行库。

程序仅使用 Windows 系统提供的文件选择对话框功能，因此需要链接系统库：

```text
Comdlg32.lib
```

### 3. 单次读取同时计算六种哈希值

在“计算单个文件”模式下，程序使用约 4 MiB 的缓冲区分块读取文件。

每次从磁盘读取一块数据后，依次更新：

- CRC32 状态；
- MD5 状态；
- SHA-1 状态；
- SHA-256 状态；
- SHA-384 状态；
- SHA-512 状态。

因此不会为了每种算法分别完整读取文件。

### 4. 支持大文件

程序不会将整个文件一次性加载到内存中，而是使用固定大小的缓冲区进行流式处理。

默认缓冲区大小为：

```cpp
constexpr std::size_t FILE_BUFFER_SIZE = 4u * 1024u * 1024u;
```

即：

```text
4 MiB
```

实际内存占用与文件大小无关，适合处理较大的 ISO、压缩包、安装包、视频文件、磁盘镜像和备份文件。

### 5. 支持 Unicode 文件路径

文件选择窗口使用 Windows 宽字符 API：

```cpp
GetOpenFileNameW
```

文件路径使用：

```cpp
std::filesystem::path
```

可以处理包含中文及其他 Unicode 字符的文件名和目录名。

例如：

```text
D:\测试文件\版本 1.0\安装包.exe
```

### 6. 支持逐字节精确比较

比较两个文件时，程序不仅比较哈希值，还支持进行逐字节比较。

精确比较流程如下：

1. 获取两个文件的大小；
2. 如果大小不同，直接判定内容不同；
3. 如果大小相同，再以 4 MiB 为单位分块读取；
4. 使用 `std::memcmp` 对每个数据块进行逐字节比较；
5. 所有数据块均相同，才判定两个文件内容完全相同。

因此程序不会只依赖 CRC32、MD5 或其他摘要值来声称两个文件“绝对相同”。

- SHA-256；
- SHA-384；
- SHA-512。

随后输出哈希对比结果：

```text

SHA384  : 不同
```

如果两个文件大小不同，逐字节比较会直接得出内容不同的结论：


如果两个文件大小相同，程序会继续进行分块比较，直到：

- 找到第一个不同的数据块；或者
- 完成整个文件的比较。

## 输出说明

### CRC32

输出长度：

```text
8 个十六进制字符
```

示例：

```text
352441c2
```

CRC32 主要用于检测随机传输错误和普通数据损坏，不适合用于安全敏感的完整性认证。

### MD5

输出长度：

```text
32 个十六进制字符
```

示例：

```text
900150983cd24fb0d6963f7d28e17f72
```

MD5 已不适合需要抗碰撞能力的安全场景，但仍常见于：

- 历史软件包校验；
- 非安全性数据去重；
- 与旧系统兼容；
- 普通文件快速摘要。

### SHA-1

输出长度：

```text
40 个十六进制字符
```

SHA-1 已不建议用于新的安全设计。保留该算法主要用于兼容已有文件校验值。

### SHA-256

输出长度：

```text
64 个十六进制字符
```

SHA-256 是本项目中较推荐的通用文件校验算法，适用于：

- 下载文件校验；
- 软件包校验；
- 备份文件验证；
- 发布文件完整性检查；
- 文件传输后的摘要确认。

### SHA-384

输出长度：

```text
96 个十六进制字符
```

SHA-384 是 SHA-2 家族算法，具有较长的摘要长度。

### SHA-512

输出长度：

```text
128 个十六进制字符
```

SHA-512 适用于需要更长摘要的场景。

## 算法说明

## CRC32

本项目使用标准 CRC-32 多项式：

```text
0xEDB88320
```

计算过程包括：

1. 初始值设置为 `0xFFFFFFFF`；
2. 对输入数据逐字节更新；
3. 最终结果与 `0xFFFFFFFF` 异或；
4. 以 8 位小写十六进制形式输出。

## MD5

MD5 的主要特点：

- 512 位消息分组；
- 128 位摘要；
- 小端字节序；
- 输出 32 位十六进制字符串。

项目中包含 MD5 的标准填充处理：

1. 添加一个 `0x80` 字节；
2. 添加若干个 `0x00` 字节；
3. 将原始消息长度以小端 64 位整数写入末尾；
4. 对填充后的消息进行最终变换。

## SHA-1

SHA-1 的主要特点：

- 512 位消息分组；
- 160 位摘要；
- 大端字节序；
- 输出 40 位十六进制字符串。

## SHA-256

SHA-256 的主要特点：

- 512 位消息分组；
- 256 位摘要；
- 大端字节序；
- 64 轮压缩变换；
- 输出 64 位十六进制字符串。

## SHA-384 和 SHA-512

SHA-384 与 SHA-512 使用：

- 1024 位消息分组；
- 64 位工作变量；
- 80 轮压缩变换；
- 大端字节序。

两者的区别包括：

| 项目 | SHA-384 | SHA-512 |
|---|---:|---:|
| 摘要长度 | 384 位 | 512 位 |
| 输出字符数 | 96 | 128 |
| 初始向量 | SHA-384 专用 | SHA-512 专用 |
| 输出处理 | 输出前 6 个 64 位状态字 | 输出全部 8 个 64 位状态字 |

需要注意：

> SHA-384 不是简单地将普通 SHA-512 的结果截断。它使用独立的初始向量。

## 安全性与适用场景

## 推荐使用 SHA-256、SHA-384 或 SHA-512

对于新的文件完整性校验场景，建议优先使用：

```text
SHA-256
SHA-384
SHA-512
```

例如：

- 检查下载文件是否损坏；
- 比较文件传输前后的摘要；
- 核对备份文件；
- 验证发布包是否与官方文件一致；
- 生成内部文件清单。

## CRC32、MD5 和 SHA-1 的限制

### CRC32

CRC32 适合检测：

- 随机传输错误；
- 存储介质造成的数据损坏；
- 普通压缩包或数据格式的校验。

CRC32 不是密码学安全哈希，不能抵抗有意构造的碰撞。

### MD5

MD5 已经不适用于：

- 数字签名；
- 安全认证；
- 防篡改认证；
- 抗恶意碰撞场景；
- 密码存储。

### SHA-1

SHA-1 不建议用于新的安全设计，包括：

- 数字签名；
- 证书；
- 安全认证；
- 抗碰撞完整性保护。

### 哈希值不能替代数字签名

如果攻击者可以同时修改：

1. 文件；
2. 记录哈希值的清单；

那么单独比较哈希值并不能证明文件来自可信来源。

在需要确认文件来源和真实性时，应配合：

- 数字签名；
- 可信发布渠道；
- HTTPS；
- 签名证书；
- PGP 签名；
- 官方公布的可信摘要值。

本程序主要用于本地文件摘要和内容比较，不提供数字签名验证功能。

## 大文件与性能

### 分块读取

程序默认使用 4 MiB 缓冲区：

```cpp
constexpr std::size_t FILE_BUFFER_SIZE = 4u * 1024u * 1024u;
```

读取流程大致如下：

```text
打开文件
  ↓
读取 4 MiB 数据块
  ↓
更新六种哈希状态
  ↓
继续读取下一块
  ↓
处理文件尾部
  ↓
完成填充
  ↓
输出摘要
```

### 内存占用

单文件哈希计算不会根据文件大小分配同等大小的内存。

例如：

- 10 MiB 文件；
- 10 GiB 文件；
- 1 TiB 文件；

均采用分块方式处理。

主要内存开销来自：

- 文件读取缓冲区；
- 各哈希算法的内部状态；
- SHA-1、SHA-256 和 SHA-512 的消息调度数组；
- 临时数据结构。

### 比较模式的读取次数

比较两个文件时，程序通常会进行以下操作：

1. 读取第一个文件并计算哈希；
2. 读取第二个文件并计算哈希；
3. 再读取两个文件进行逐字节比较。

因此，“单次读取同时计算全部哈希值”适用于单个文件内部的多算法计算，并不意味着比较两个文件时只会访问每个文件一次。

### 性能影响因素

实际速度会受到以下因素影响：

- 磁盘类型；
- 文件所在位置；
- 文件大小；
- 杀毒软件实时扫描；
- 同时运行的其他程序；
- CPU 性能；
- 编译器优化等级；
- 是否使用 Debug 构建；
- 文件是否位于网络映射盘。

程序显示的速度是整个读取和哈希计算过程的粗略平均速度。

## 常见问题

### 1. 为什么中文路径仍然显示乱码？

可以尝试以下措施：

1. 使用 Windows Terminal；
2. 使用 Visual Studio 直接运行；
3. 确保源文件保存为 UTF-8；
4. 使用项目中提供的 `/utf-8` 编译选项；
5. 避免使用不支持 Unicode 的第三方控制台程序。

程序本身已经使用宽字符 API 和宽字符控制台输出，但不同终端对 Unicode 的支持可能存在差异。

### 2. 为什么测试 `abc` 的结果不一致？

最常见原因是测试文件末尾多了换行符。

例如，以下内容看起来相同：

```text
abc
```

但文件可能分别包含：

```text
61 62 63
```

或者：

```text
61 62 63 0A
```

甚至：

```text
61 62 63 0D 0A
```

它们的哈希值完全不同。

建议使用二进制方式创建测试文件：

```powershell
[System.IO.File]::WriteAllBytes(
    "test.txt",
    [System.Text.Encoding]::ASCII.GetBytes("abc")
)
```

### 3. 哈希值相同是否一定说明文件相同？

一般情况下，强哈希算法的碰撞概率极低，但从严格数学意义上说，任何固定长度哈希都有碰撞可能。

本项目在比较模式下会额外进行逐字节精确比较，因此：

```text
哈希值相同 + 逐字节比较相同
```

才会输出：

```text
两个文件内容完全相同
```

### 4. 为什么比较两个文件时速度比计算一个文件慢？

因为比较模式通常需要：

1. 分别读取两个文件计算哈希；
2. 再重新读取两个文件进行逐字节比较。

这是为了同时提供：

- 多算法摘要比较；
- 内容级精确比较。

### 5. 可以处理空文件吗？

可以。

哈希算法均支持空输入。空文件会按照各算法规定的标准填充规则计算摘要。

### 6. 可以处理超大文件吗？

程序采用分块读取，理论上可以处理远大于内存容量的文件。

但实际限制还包括：

- 文件系统支持的最大文件大小；
- `std::ifstream` 的实现；
- Windows 文件系统；
- 磁盘容量；
- 文件读取权限；
- 算法内部长度计数器限制。

对于一般软件包、镜像、视频和备份文件，均可正常处理。

### 7. 为什么 CRC32 和 SHA-256 的结果格式不同？

不同算法的摘要长度不同：

| 算法 | 摘要长度 | 十六进制字符数 |
|---|---:|---:|
| CRC32 | 32 位 | 8 |
| MD5 | 128 位 | 32 |
| SHA-1 | 160 位 | 40 |
| SHA-256 | 256 位 | 64 |
| SHA-384 | 384 位 | 96 |
| SHA-512 | 512 位 | 128 |

### 8. 可以在 Linux 或 macOS 上编译吗？

当前版本不能直接跨平台编译，因为使用了：

- `Windows.h`；
- `commdlg.h`；
- `GetOpenFileNameW`；
- `GetConsoleWindow`；
- `Comdlg32.lib`；
- Windows 控制台宽字符接口。

哈希算法本身主要使用标准 C++，但文件选择和交互部分需要替换为跨平台实现后，才适合移植到 Linux 或 macOS。

## 设计说明

## 文件哈希计算接口

核心接口：

```cpp
bool CalculateFileHashes(
    const std::filesystem::path& filePath,
    HashResult& result,
    std::string& errorMessage
);
```

返回值含义：

| 返回值 | 含义 |
|---|---|
| `true` | 文件读取和哈希计算成功 |
| `false` | 计算失败，错误信息写入 `errorMessage` |

成功后，所有摘要值保存在 `HashResult` 中。

示例：

```cpp
HashResult result;
std::string errorMessage;

if (CalculateFileHashes(
        "example.bin",
        result,
        errorMessage))
{
    std::cout << result.sha256 << '\n';
}
else
{
    std::cerr << errorMessage << '\n';
}
```

## 文件精确比较接口

核心接口：

```cpp
bool FilesExactlyEqual(
    const std::filesystem::path& first,
    const std::filesystem::path& second,
    bool& equal,
    std::string& errorMessage
);
```

这里需要区分函数返回值和 `equal` 参数：

- 函数返回 `false`：比较过程发生错误；
- 函数返回 `true` 且 `equal == true`：两个文件内容完全相同；
- 函数返回 `true` 且 `equal == false`：两个文件内容不同。

示例：

```cpp
bool equal = false;
std::string errorMessage;

if (!FilesExactlyEqual(
        "first.bin",
        "second.bin",
        equal,
        errorMessage))
{
    std::cerr << errorMessage << '\n';
}
else if (equal)
{
    std::cout << "文件内容相同\n";
}
else
{
    std::cout << "文件内容不同\n";
}
```

## 十六进制输出

所有哈希值均转换为小写十六进制字符串。

例如：

```text
900150983cd24fb0d6963f7d28e17f72
```

不会输出空格、冒号或换行分隔符。

## 限制与注意事项

### 1. 当前版本是控制台程序

虽然使用了 Windows 文件选择窗口，但主界面仍然是控制台菜单，不是完整的桌面 GUI 程序。

### 2. 不提供拖放功能

当前版本没有实现将文件拖拽到窗口后自动计算的功能。

### 3. 不生成校验清单文件

当前版本只在控制台输出结果，不会自动生成：

- `.txt` 校验清单；
- `.csv` 报告；
- JSON 文件；
- XML 文件。

如有需要，可以在 `main.cpp` 中增加文件输出功能。

### 4. 不验证数字签名

程序只计算摘要，不实现：

- Authenticode 签名验证；
- PGP 签名验证；
- X.509 证书验证；
- 公钥签名验证；
- 可信来源判断。

### 5. 不适合密码存储

MD5、SHA-1、SHA-256、SHA-384 和 SHA-512 都不是密码口令专用存储方案。

密码存储应使用专门的慢速、带盐算法，例如：

- Argon2；
- scrypt；
- bcrypt；
- PBKDF2。

### 6. 纯 C++ 算法实现需要充分测试

本项目的算法实现用于学习、离线文件校验和独立工具场景。若用于高安全等级、认证系统或生产级安全基础设施，建议：

- 使用经过长期审计的密码学库；
- 进行单元测试；
- 使用 NIST 测试向量；
- 进行模糊测试；
- 进行边界条件测试；
- 进行第三方安全审查。

### 7. 文件在读取期间发生变化

如果文件在计算过程中被其他程序修改，最终哈希值对应的是读取期间实际获得的数据。

对于需要稳定结果的场景，建议：

1. 先关闭可能修改文件的程序；
2. 对正在使用的文件制作副本；
3. 对副本进行计算；
4. 必要时重复计算确认结果一致。

## 总结

`OfflineFileHash` 是一个面向 Windows 的本地文件校验工具，具有以下核心能力：

- 支持 CRC32、MD5、SHA-1、SHA-256、SHA-384、SHA-512；
- 使用 C++17；
- 支持 Windows 原生文件选择窗口；
- 支持中文和 Unicode 文件路径；
- 使用固定大小缓冲区处理大文件；
- 单次读取同时更新多种哈希状态；
- 支持两个文件的哈希比较；
- 支持逐字节精确内容比较；
- 不访问网络；
- 不依赖第三方加密库。

对于普通文件完整性检查，建议优先关注：

```text
SHA-256
SHA-384
SHA-512
```

对于需要确认文件来源、防止恶意替换或满足高安全要求的场景，还应结合数字签名、可信发布渠道和经过审计的密码学库。
